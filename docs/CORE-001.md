# CORE-001 financial and order kernel

This is an internal foundation for the first vertical slice. It does not accept live orders or expose wallet credits through an API. A trusted payment or authorized admin integration must authenticate and audit before calling `credit`.

All amounts use integer halalas (100 halalas = 1 SAR). The balance is derived from append-only ledger entries; the wallet row exists for per-user transaction locking, never as the financial source of truth. PostgreSQL rejects ledger UPDATE and DELETE. `RESERVE` moves available funds to held funds; `CAPTURE` consumes held funds; `RELEASE` returns them. Each order has at most one reservation and one settlement, enforced by unique partial indexes. Credits, reservations and settlements each require an idempotency key scoped to the wallet.

`confirm_order` serializes requests on the wallet row and commits an immutable order price snapshot, reservation and PENDING job in the same transaction. Insufficient funds roll back the order and job. A repeated request key for the same user/service/channel returns the original order. Services are disabled by default and must be explicitly enabled after their processor and quality rules are available.

The first internal processor merges two to ten PDF files from the same customer, with a 40 MiB total input bound and 200-page bound. The output is reopened and checked before a `COMPLETED` job moves the order to `AWAITING_FULFILLMENT`. The financial capture is a separate `acknowledge_delivery` transaction requiring a trusted external delivery receipt. Retry of that receipt does not capture twice. An invalid PDF permanently fails and releases held funds. Service input count and MIME constraints are registry data, rather than Telegram handler logic. No live service is seeded or enabled yet.

Next before serving customers: connect a reliable Telegram upload and delivery workflow, admin visibility, authentication and payment top-ups. Add full document safety checks and isolate PDF processing; the byte-signature gate alone is not a safety guarantee. A trusted payment or authorized admin integration must authenticate and audit before calling `credit`. Direct ledger writes must be restricted to the application's database role in production; the immutability trigger protects against normal UPDATE/DELETE, not database administrators.

The job dispatcher reads PENDING rows from PostgreSQL on each scheduled pass and enqueues an ARQ task keyed by job and attempt. A worker transaction claims the pending row, increments the attempt number and records an attempt; concurrent deliveries cannot claim it twice. A retryable failure returns the row to PENDING; exhausting attempts or a permanent failure marks the order FAILED and releases its reservation exactly once. The worker execution timeout is 120 seconds; a separate scan recovers PROCESSING attempts after 300 seconds, retrying or releasing held funds on exhaustion. Unregistered processors fail closed with `PROCESSOR_UNAVAILABLE` and release the reservation.

The migrated PostgreSQL integration suite covers double submits, concurrent balance contention, refund of held funds through release, settlement replay, price snapshots, insufficient funds rollback, reasoned adjustments and database-enforced immutability. Use a dedicated disposable database when running tests; records use unique IDs but tests do not delete financial history.
