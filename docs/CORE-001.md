# CORE-001 financial and order kernel

This is an internal foundation for the first vertical slice. It does not accept live orders or expose wallet credits through an API. A trusted payment or authorized admin integration must authenticate and audit before calling `credit`.

All amounts use integer halalas (100 halalas = 1 SAR). The balance is derived from append-only ledger entries; the wallet row exists for per-user transaction locking, never as the financial source of truth. PostgreSQL rejects ledger UPDATE and DELETE. `RESERVE` moves available funds to held funds; `CAPTURE` consumes held funds; `RELEASE` returns them. Each order has at most one reservation and one settlement, enforced by unique partial indexes. Credits, reservations and settlements each require an idempotency key scoped to the wallet.

`confirm_order` serializes requests on the wallet row and commits an immutable order price snapshot, reservation and PENDING job in the same transaction. Insufficient funds roll back the order and job. A repeated request key for the same user/service/channel returns the original order. Services are disabled by default and must be explicitly enabled after their processor and quality rules are available.

The first internal processor merges two to ten PDF files from the same customer, with a 40 MiB total input bound and 200-page bound. The output is reopened and checked before a `COMPLETED` job moves the order to `AWAITING_FULFILLMENT`. The same transaction writes a Telegram delivery outbox row. A separate worker sends the output and uses the Telegram message ID as the receipt in the financial capture transaction. Failed sends use bounded retries and backoff; exhausted sends release held funds. A stale `SENDING` row is recovered after three minutes. An invalid PDF permanently fails and releases held funds. Service input count and MIME constraints are registry data, rather than Telegram handler logic. No live service is seeded or enabled yet.

The Telegram upload and confirmation workflow persists each message's file and quoted price in PostgreSQL. `/start` can resume an unfinished workflow, a repeated upload message attaches once, repeated confirmation returns the same order, and any service price change requires a fresh quote. Incoming file downloads have a byte limit. The feature flag defaults to off, so bot users cannot upload or order against the incomplete deployment.

Admin read access uses server-enforced OWNER/OPERATOR permissions, password-hashed credentials, opaque revocable sessions and an append-only audit log. The dashboard shows order and payment counts, failed jobs and deliveries, and the latest 100 orders; audit viewing is OWNER-only. The wallet top-up kernel is atomic and idempotent but no live provider, checkout route, webhook route or administrative wallet write is exposed. In Compose PDF merging runs in a separate no-network container without application credentials and rejects active PDF features, forms and embedded files before and after merging. Next before serving customers: integrate and test a real payment provider, implement malware scanning and production recovery procedures; the byte-signature and format gates alone are not a safety guarantee. Telegram cannot provide exactly-once document sending across a crash after its API accepts a message and before our receipt is committed; a retry may deliver a duplicate file, but the ledger capture remains idempotent. A trusted payment or authorized admin integration must authenticate and audit before calling `credit`. Direct ledger writes must be restricted to the application's database role in production; the immutability trigger protects against normal UPDATE/DELETE, not database administrators.

The job dispatcher reads PENDING rows from PostgreSQL on each scheduled pass and enqueues an ARQ task keyed by job and attempt. A worker transaction claims the pending row, increments the attempt number and records an attempt; concurrent deliveries cannot claim it twice. A retryable failure returns the row to PENDING; exhausting attempts or a permanent failure marks the order FAILED and releases its reservation exactly once. The worker execution timeout is 120 seconds; a separate scan recovers PROCESSING attempts after 300 seconds, retrying or releasing held funds on exhaustion. Unregistered processors fail closed with `PROCESSOR_UNAVAILABLE` and release the reservation.

The admin "Needs Attention" section lists up to 20 recent failed jobs, deliveries, and payments per category. Stable IDs, service name, attempt counts and error codes help operators identify an incident. The endpoint requires server-side `admin:view` authorization and omits customer input, provider references and raw exception messages. Investigation and recovery still require controlled operational procedures; the dashboard does not retry or change financial state.

The migrated PostgreSQL integration suite covers double submits, concurrent balance contention, refund of held funds through release, settlement replay, price snapshots, insufficient funds rollback, reasoned adjustments and database-enforced immutability. Use a dedicated disposable database when running tests; records use unique IDs but tests do not delete financial history.
