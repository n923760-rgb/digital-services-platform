# Payment provider boundary

V1 uses a SAR wallet; the digital store stays independent. The `payments` table represents a pending `WALLET_TOPUP` intent and a provider reference. `payment_events` records verified paid-event IDs append-only. A database transaction binds one paid intent to one `TOP_UP` ledger entry keyed by `payment:{payment_id}`. Duplicate webhook delivery, a different event ID for the same paid intent, and concurrent callbacks cannot create additional credits. Mismatched provider, checkout reference, amount or currency fails closed.

The owner selected **Telegram Stars, direct payment per order**. The current customer integration is the separate native XTR invoice/charge path documented in [TELEGRAM-STARS.md](TELEGRAM-STARS.md); it never converts Stars into this SAR wallet. This older SAR top-up kernel has no public checkout route/webhook or live SAR provider. Any future SAR provider adapter must verify the raw request body and signature according to that provider's current documentation, authenticate/authorize checkout initiation, bind the actual provider reference before callbacks are accepted, validate provider account and payment completion status, and map only settled/paid events into `VerifiedTopup`. Reject or quarantine failed and disputed events according to the chosen provider's contract. Log receipt IDs without credentials, store all signing secrets outside source control, and add integration tests for valid, forged, replayed and out-of-order callbacks before enabling payments. The HMAC adapter in `tests/test_payments.py` is **test-only**, not an integration for real payments.

Customer-facing SAR top-ups remain unavailable. The gated Stars path also requires actual Telegram payment/refund staging, support/disputes and production recovery qualification before paid launch. The web dashboard shows payment counters but provides no payment or wallet write actions.
