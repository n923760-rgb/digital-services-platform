# Payment provider boundary

V1 uses a SAR wallet; the digital store stays independent. The `payments` table represents a pending `WALLET_TOPUP` intent and a provider reference. `payment_events` records verified paid-event IDs append-only. A database transaction binds one paid intent to one `TOP_UP` ledger entry keyed by `payment:{payment_id}`. Duplicate webhook delivery, a different event ID for the same paid intent, and concurrent callbacks cannot create additional credits. Mismatched provider, checkout reference, amount or currency fails closed.

The production payment provider is undecided. No public checkout route or webhook route exists. A future provider adapter must verify the raw request body and signature according to that provider's current documentation, authenticate/authorize checkout initiation, bind the actual provider reference before callbacks are accepted, validate provider account and payment completion status, and map only settled/paid events into `VerifiedTopup`. Reject or quarantine failed and disputed events according to the chosen provider's contract. Log receipt IDs without credentials, store all signing secrets outside source control, and add integration tests for valid, forged, replayed and out-of-order callbacks before enabling payments. The HMAC adapter in `tests/test_payments.py` is **test-only**, not an integration for real payments.

Until these pieces and a tested refund/reconciliation procedure exist, do not expose customer-facing top-ups or enable paid Telegram orders. The web dashboard shows payment counters but provides no payment or wallet write actions.
