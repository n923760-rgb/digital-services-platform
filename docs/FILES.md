# File storage contract

The file module accepts only bounded PDF, PNG, JPEG and WebP bytes with matching extension, MIME type and signatures. Its object-storage dependency is a protocol; the S3 adapter translates missing-object errors. Each file belongs to one user and receives an unguessable storage key. PostgreSQL tracks UPLOADING, READY, FAILED and EXPIRED states. An upload failure leaves a visible FAILED row; no customer endpoint exposes uploads yet.

`FILE_RETENTION_DAYS` (default 30) and `MAX_UPLOAD_BYTES` (default 20 MiB) are deployment settings, not product commitments. An hourly worker deletes objects past retention, then marks metadata EXPIRED. An object-specific deletion failure leaves that file's metadata retryable, records only a sanitized metadata ID, and continues other locked expired files; successful metadata updates commit together. Database transaction failures still propagate and roll back metadata, so provider deletion must be idempotent. Periodic scanning limits batches to 100. Production object-store lifecycle policies should provide a second cleanup path, including interrupted uploads and orphaned objects.

Telegram's «ملفاتي» lists the latest ten completed PDF results owned by the current Telegram user. The list omits input files, unfinished orders, expired files, non-ready files and results larger than 20 MiB. Re-send buttons recheck the sender's identity, order completion, file retention and storage object before delivering to that sender's private chat. The feature is read-only with respect to financial records; no new charge or order is created. The list does not guarantee an object is still in storage: a missing object returns a customer-safe error and is logged for operations. This is a retrieval path for already delivered PDF results, not a public file URL or a new upload endpoint.

Signatures are an initial gate only. In Compose the ARQ worker sends PDFs through a private shared volume to `pdf-sandbox`: a separate no-network, non-root, read-only container without database, Telegram, storage, AI or payment credentials. It drops Linux capabilities, forbids privilege escalation, bounds PIDs/memory/temp storage, and invokes a short-lived parser with CPU/address-space/file-size limits. Worker requests time out after 95 seconds; invalid PDFs fail permanently, while sandbox outages/crashes retry under the job policy before releasing reserved funds. Each job's shared input is removed after the worker returns; orphaned requests are removed after 30 minutes by the sandbox. `pdf-sandbox-init` sets ownership on the private volume before either service starts. CI runs a real worker-to-sandbox PDF merge. Direct internal Python calls use a local bounded subprocess for integration tests; the Compose worker explicitly configures the sandbox path and fails closed if it is absent.

The merge processor now applies a strict **print-only PDF policy** inside the sandbox. It rejects encrypted PDFs, annotations (including clickable links and forms), JavaScript, document-open actions, embedded files and rich media. It walks a bounded reachable object graph without extracting embedded files or decoding content streams, then checks the merged PDF for the same features. This is a format policy, **not an antivirus or proof that a PDF is harmless**. Legitimate PDFs with forms or links are rejected in V1; offer customers a clear input-error message before enabling the service. The container boundary and policy still need malware screening, decompression review, dedicated host hardening and operational recovery tests. Keep paid customer uploads disabled until those checks are complete. Before delivering files in other channels, add authorization and signed access or streamed downloads. Current operations are internal and require a trusted caller.


## Telegram upload admission and abandoned intents

The enabled PDF upload path checks count, declared bytes and remaining byte budgets before downloading or creating a file. Each workflow permits at most its registry maximum (up to ten PDF inputs) and 40 MiB total. MAX_USER_UPLOAD_BYTES defaults to 100 MiB of retained INPUT metadata per customer, including inputs on cancelled/submitted workflows and pending/failed unexpired intents. This is a configurable deployment resource guard, not a paid storage commitment or a guarantee about total physical storage during provider cleanup failures.

A PostgreSQL session advisory lock permits only one in-flight bot upload per customer across processes. Competing uploads fail before downloading; cancellation and confirmation do not wait on a long database transaction. The downloaded stream is bounded by the smallest remaining file/workflow/customer budget, even when a document declares fewer bytes than it sends.

Attachment must target the original workflow ID. Cancellation/replacement cannot move an in-flight file into a newer workflow. A new upload intent initially expires after one hour; successful attachment and extension to normal retention commit together. Attachment failure/cancellation attempts immediate cleanup, without deleting an attached/order-owned file. Storage deletion failures retain expired metadata for hourly retry. A process crash or cancellation during storage I/O leaves its short-lived intent available to scheduled cleanup; production object lifecycle remains required for provider writes completed after cleanup or loss of metadata.

This admission protection does not prove aggregate-memory safety for other internal processor callers (DSP-005), account-creation/rate-abuse protection, antivirus clearance, or production recovery. Keep public paid uploads gated pending those qualifications.

## Processor input budgets

The PDF processor independently checks every ordered input before a storage HEAD/GET: two to ten ready, unexpired, owner-matching INPUT PDFs, each no larger than MAX_UPLOAD_BYTES, with no more than 40 MiB total. The query returns at most eleven rows so excessive counts fail without fetching an unbounded list. Wrong-type inputs are rejected rather than silently omitted.

Each read then rechecks current owner/readiness/expiry and metadata size against the smaller of the per-file cap and remaining 40 MiB budget. Object HEAD size must match metadata; GET requests only that bounded size plus the adapter's one-byte overrun sentinel. Size mismatch fails without invoking either parser or creating output. Callers of read_file/verify_file can opt into a max_bytes guard; existing callers without it retain their behavior.

These are raw input byte bounds, not a measured process RSS guarantee. The parent still retains accepted documents in memory; parser copies, output, decompression and concurrent processes require their existing sandbox limits and separate load qualification. PDF parsing and output validation remain in the existing isolated execution path.

## Sandbox liveness during bounded processing

The scanner now renews its heartbeat on a separate daemon thread while a parser job holds a bounded progress lease (existing 75-second parser timeout plus ten seconds for local IPC). The scanner renews only a ten-second lease between jobs. A blocked scan or job that outlives its lease stops touching the heartbeat; shutdown removes the marker. This keeps normal long processing from producing false stale health while preserving detection of stalls. Container health does not automatically restart unhealthy containers; operators still need monitoring/recovery. No parser/container privilege, CPU, memory, network or timeout limit is relaxed.

## Cleanup failure isolation limits

Only exceptions from an object's provider delete are isolated; metadata/database failures abort the transaction and shutdown cancellation propagates. Live or already EXPIRED files are excluded. A successful object delete precedes its EXPIRED metadata update. Retention days, hourly schedule, batch bound and row locks are unchanged.

Migration 0015 adds a nullable cleanup_attempted_at timestamp and a partial queue index for non-EXPIRED metadata. Eligible rows are ordered by COALESCE(cleanup_attempted_at, retention_until), then metadata UUID: never-attempted files wait from their expiry; retries wait from their last committed attempt. Each selected row records its attempt in the same transaction before provider deletion. A provider failure leaves status and original retention unchanged but moves that retry behind earlier waiting work when the batch commits. New expiries do not automatically jump ahead of older retries. Successful objects become EXPIRED; database/programming failures or cancellation still roll back the whole batch, including attempt timestamps.

A disposable PostgreSQL regression seeds 100 failing oldest objects and a later healthy expired object, verifies the first run is bounded, the next run reaches healthy work, and failed objects remain retryable and eventually clear after recovery. Another regression proves unexpected failures roll back retry age and metadata even when an earlier object delete already succeeded; retries rely on idempotent deletion. These are queue correctness checks, not production throughput, elapsed-time SLA or a guarantee under permanent lock contention. An hourly 100-row worker remains capacity-limited. Operators must monitor cleanup failures/backlog and qualify provider lifecycle and outage recovery before paid launch; no production retention policy is selected by this repair.
