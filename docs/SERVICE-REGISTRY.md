# Service registry administration

The database controls service descriptions, prices and availability. `GET /api/admin/services` is available to OWNER and OPERATOR. `PATCH /api/admin/services/{id}` requires OWNER's `admin:manage` permission, a same-origin browser request, a reason, the latest integer `expected_revision`, and `confirm=true` for a change to availability. Stale edits return HTTP 409; clients must reload. Each successful change and an immutable audit entry with before/after values are committed in a single PostgreSQL transaction. Updates to descriptions and prices do not alter an existing order's `price_snapshot_halalas`.

Service activation is **off by default** (`SERVICE_ACTIVATION_ENABLED=false`). Disabling an active service remains possible. Activation also requires an enabled category, a known tool processor, and the supported PDF input schema; unimplemented processors cannot be enabled. This extra configuration gate is for a controlled future rollout. Changing the gate alone does **not** certify the deployment as safe: the Telegram order flag remains off, and malware screening, production storage, payment funding and the security checklist still have to be finished before handling paid customers. No live service is seeded by this change. Never treat editing the service table manually as a substitute for the administrative checks and audit log.

Prices are integer halalas (100 halalas = 1 SAR) with a 10,000 SAR administrative cap. The V1 edit API accepts description, price and enabled state; service creation, category ordering and template assignment require separate, explicit implementation after their schemas and processors are ready.
