# Service registry administration

The database controls service descriptions, prices and availability. `GET /api/admin/services` and `GET /api/admin/categories` are available to OWNER and OPERATOR. OWNER may register categories and services through `POST /api/admin/categories` and `POST /api/admin/services`; all writes require `admin:manage`, a same-origin browser request and a reason. Newly registered services are always **disabled**, regardless of their processor type. The slug is unique; repeating an identical registration returns the same ID without a second audit event, while conflicting data return HTTP 409. A request cannot supply an `enabled` field at creation. The input schema is stored as a bounded JSON object and does not execute arbitrary workflows.

`PATCH /api/admin/services/{id}` requires OWNER's `admin:manage` permission, a same-origin browser request, a reason, the latest integer `expected_revision`, and `confirm=true` for a change to availability. Stale edits return HTTP 409; clients must reload. Each successful change and an immutable audit entry with before/after values are committed in a single PostgreSQL transaction. Updates to descriptions and prices do not alter an existing order's `price_snapshot_halalas`.

Service activation is **off by default** (`SERVICE_ACTIVATION_ENABLED=false`). Disabling an active service remains possible. Activation also requires an enabled category, a known tool processor, and the supported PDF input schema; unimplemented processors cannot be enabled. This extra configuration gate is for a controlled future rollout. Changing the gate alone does **not** certify the deployment as safe: the Telegram order flag remains off, and malware screening, production storage, payment funding and the security checklist still have to be finished before handling paid customers. No live service is seeded by this change. Never treat editing the service table manually as a substitute for the administrative checks and audit log.

Prices are integer halalas (100 halalas = 1 SAR) with a 10,000 SAR administrative cap. For the supported `merge-pdf` slug, registration requires `processor_type=tool` and the exact schema `{"min_files":2,"max_files":10,"file_mime":"application/pdf"}`. A newly registered AI, template, manual or hybrid service is only catalog data until its processor and safe activation path are implemented. The edit API accepts description, price and enabled state; category ordering and template assignment require separate, explicit implementation after their schemas and processors are ready.
