# DSP-013 independent expired-object cleanup failures
Baseline: 517ee6e504fe7d4ca488c78a36509b31f4fc87da, verified main after qualified PR #34. Central governance 641e4f9e45da109257ba1f38752b94604c2e4531.
FACT from files.py: the cron's 100-row locked deletion batch aborted on any storage delete exception; metadata updates for earlier successful external deletes rolled back and later healthy objects were not attempted. A persistent object-specific error could repeatedly block healthy members of that batch.
Correction: catch only exceptions from provider deletion, emit a sanitized event containing the metadata UUID, retain failed metadata for retry, continue other locked candidates, and count only successful delete+metadata operations. DB update/transaction failures still propagate; cancellation BaseException is not swallowed. Delete occurs before marking EXPIRED; ownership/retention and existing SKIP LOCKED coordination unchanged.
Pending exact-head external CI: real PostgreSQL with an expired blocked object, later healthy expired object and live object; success committed visible on a second connection, failed object retained then retried, live object untouched, provider exception/key absent from logs. Full Python/web/Compose checks required.
This is bounded failure isolation, not production retention certification. Hourly 100-item batch still has throughput/backlog limits; 100 permanently failing old candidates can block later batches. Monitoring, provider lifecycle, policy, outage/recovery and capacity require separate production-like qualification. Do not silently choose new retention days or broaden deletion scope.
No production cleanup/deployment, credentials, provider selection, financial history changes or paid activation. Storage double in regression tests; Compose still uses development S3Mock.
